# V02-005 备份管理与受控恢复验收

> 日期：2026-09-08
> 状态：已完成 Windows 本地开发版阶段验收。
> 对应范围：开发规划第 4.5 节；未操作正式用户数据库，未发布安装包。

## 1. 本阶段交付

设置页新增“备份与恢复”，提供手动一致性备份、列表校验、明确保留、数量/容量策略、目录入口和恢复预检。列表显示创建时间、大小、CodeHelm 构建版本、schema、来源和校验状态。旧备份缺少版本时显示未知；不会猜测来源版本。

备份沿用 SQLite backup API，包含已提交的 WAL 数据。只有独立候选通过完整性、外键和摘要校验后，才发布到正式备份目录。未完成目录以 `.pending-` 开头，不能作为恢复候选。

备份范围为 CodeHelm SQLite 管理数据：项目、分析记录、运行方案、环境变量配置、设置、运行与服务历史。项目源码、依赖、服务产生的数据以及日志文件不在恢复范围内。备份可能含敏感值或密文，不宣称无敏感信息。

## 2. 用户操作流程

1. 在设置页点击“创建管理数据备份”，等待完成并校验通过。
2. 重要恢复点可点击“明确保留”；恢复前自动保全的备份强制保留，不能从界面解除。
3. 选择备份并点击“预检恢复”。主进程校验原备份，创建独立候选副本，在副本上完成迁移和可读性检查。
4. 预检结果展示源/目标 schema、项目和方案数量，以及本机无法解密的敏感值数量。预检不会更改当前管理数据。
5. 点击“继续恢复确认”后出现主进程系统确认框，默认选择取消。确认框说明将停止任务与受管进程、丢失备份后新增管理数据，并要求操作后重新打开应用。
6. 用户确认后进入维护状态：拒绝新业务 IPC，停止受管执行和分析任务，等待已受理异步工作退出，核对进程停止结果，并关闭日志写入。
7. 创建经验证的恢复前保全备份，然后在 SQLite 独占事务中替换管理数据。外部锁或保全过程中的外部写入会导致恢复拒绝；事务内再次验证完整性和外键。
8. 恢复完成后显示保全目录。关闭应用并重新打开以载入新数据；确认后的失败也保留维护状态，要求关闭重开，不继续使用已经停止的业务组件。

恢复清除历史执行确认，用户需要重新确认后才能启动。无法在本机解密的敏感值只在候选副本中清空并标为必填，预检结果和确认框都会告知数量；恢复后必须重新输入。原备份和恢复前保全副本不因此被改写。

## 3. 存储与失败保护

| 项目 | 行为 |
|---|---|
| 默认策略 | 20 个备份、2,048 MiB，沿用 30 分钟定时备份 |
| 可设置范围 | 3～200 个备份、64～20,480 MiB |
| 安全下限 | 沿用至少三个保留恢复点；新成功备份不在本次清理中删除 |
| 清理排除 | 明确保留、恢复前保全、未完成或未知目录、正在发布的新备份 |
| 策略生效 | 下一次成功备份后清理；受保护备份或下限导致超限时显示说明 |
| 策略位置 | 备份根目录 `.policy.json`，属于本机备份策略，不随数据库恢复回退 |
| 列表 | 最多展示最近 200 个非隐藏目录；逐项重新校验，不仅相信清单中的“verified” |
| 恢复候选 | `.restore-<token>/candidate.sqlite`；原始备份与候选分离 |
| 预检令牌 | 主进程保留最近一次预检，5 分钟有效；实际恢复一次消费 |
| 恢复诊断 | 候选目录中的 `result.json` 记录开始、失败或完成；不写敏感值 |
| 业务排空 | 新业务 IPC 被阻断，已受理异步 IPC 最多等待 10 秒；未排空则拒绝恢复 |
| SQLite 等锁 | 设置 1 秒 busy timeout；不能取得独占事务就拒绝替换 |
| 应用退出 | 等待已开始的备份管理操作和定时备份结束，再关闭数据库 |

替换阶段使用 DELETE journal 模式的独占事务，复制候选的各管理表数据；保全前后比较同一连接的 `data_version`，防止保全后又有外部写入的数据被覆盖。插入或最终检查失败会回滚整次替换。恢复不会删除主库、调用空库初始化或把失败包装成空项目列表。

迁移在候选副本上进行，仍使用现有事务化迁移。未来 schema 在预检时被拒绝。旧二进制不能直接打开不兼容的新 schema；版本回退需要相应旧二进制和迁移前备份成对使用，不能把数据库恢复误认为源码或服务数据回滚。

`.pending-` 和 `.restore-` 保留用于排障，不自动清理，长期重复预检可能增加目录占用。需核对并归档后人工处理。诊断文件不是独立的事务提交证明；例如进程突然中断或提交后诊断写入失败，需结合主库、候选和保全备份核对，不能仅根据 `preparing` 推断数据丢失。

## 5. 验收结果

### 隔离数据库

[backup-management.test.ts](../../packages/database/src/__tests__/backup-management.test.ts) 覆盖八个场景：

1. 正常恢复项目、方案、设置和服务历史；退出码、错误信息等字段一致，保全备份仍包含替换前的数据，关闭重开后可读。
2. 摘要不匹配、损坏候选、未来 schema 和迁移失败均拒绝；原库不变。
3. 注入磁盘可用空间不足，以及真实第二 SQLite 连接持有写锁，均拒绝恢复。
4. 通过数据库触发器注入恢复写入失败，验证事务回滚、失败记录和重开后的原数据。
5. 中断 backup API 不会发布半成品；明确保留的恢复点不被自动清理。
6. 较旧 schema 预检迁移；模拟跨机器解密失败，只在候选中清空敏感值并标为必填。
7. 保全期间真实外部连接写入，恢复拒绝且保留该外部写入。
8. 子进程在独占事务删除数据后直接退出；重新打开 SQLite 后原数据仍在，没有静默创建空库。

[maintenance-gate.test.ts](../../apps/desktop/src/main/ipc/__tests__/maintenance-gate.test.ts) 验证维护状态阻断新请求并等待旧请求完成。既有 25 项启动保护测试也通过，涵盖启动前备份、迁移、保留策略与异常保护。

### 实际 Electron

[desktop-lifecycle.spec.ts](../../e2e/desktop-lifecycle.spec.ts) 使用真实 Electron 构建和独立临时用户目录：

- 从设置页创建备份、核对版本、明确保留并打开恢复预览。
- 取消主进程确认后项目名称保持修改后的值。
- 确认恢复后真实受管 fixture 进程退出，业务 IPC 被维护门禁阻断。
- 真正关闭并重启应用，项目名称、方案和设置回到备份状态，恢复前保全记录可见。
- 检查备份页面明暗主题及恢复结果截图，未发现控件重叠；来源版本显示 CodeHelm `0.1.0`。

## 6. 阶段边界与下一步

本阶段提供应用可启动时的本地备份管理与受控恢复。若主库本身损坏到不能通过启动保护，仍保持既有“停止启动并保留文件”的行为；本阶段没有新增脱离应用的数据库修复工具。

未进行真实断电、物理磁盘耗尽、第二台机器 DPAPI 或安装版升级验收。磁盘不足和解密失败使用隔离故障注入，事务中断使用真实子进程退出，不能将其表述为已完成全部硬件故障矩阵。

下一阶段为 **V02-006：桌面 E2E、性能与升级交付**。现有测试作为基础，继续完成安装版、升级/回退矩阵与发布证据；v0.1 的独立门禁保持原范围。
